# ADR-0006：默认不引入 React/Vue 等 UI 框架

> **用途**：约束前端依赖的最小化。任何"加个框架/加个 UI 库"的提议先读本文。
> **状态**：Confirmed（用户要求：默认不引入，除非明确技术论证）
> **更新**：2026-11-26
> **相关**：[决策索引](./index.md) · [前端架构](../architecture/frontend-architecture.md) · [依赖策略](../engineering/dependency-policy.md) · [设计系统](../design/design-system.md)

## 背景

本站的交互都是**局部、无共享状态**的：主题切换、搜索浮层、灯箱、阅读进度、音乐播放器、视图切换。页面之间没有客户端路由，没有需要跨组件同步的复杂状态。

## 决策

- 不引入 React / Vue / Svelte / Solid 等 UI 框架，也不引入其生态的组件库。
- 页面与组件使用 `.astro`（构建期渲染）；交互使用原生 ES Module + DOM API。
- 若未来某个功能确实需要框架级状态管理，必须先写一条新 ADR，论证：现状为何不够、渲染成本、体积增量、维护成本、可撤销性。

## 备选方案

| 方案 | 为什么没选 |
| --- | --- |
| React（含 islands） | 为 6 个独立小交互引入完整运行时；产物与心智成本都不划算 |
| Vue / Svelte | 同上，只是运行时更小，但仍然没有必要 |
| Alpine.js 之类轻库 | 可用，但原生 DOM 已足够；多一个依赖就多一份版本与行为风险 |
| Web Components 自建 | 对当前需求过度设计 |

## 选择原因

1. **产物即 HTML**：零运行时是性能与可访问性的最省力路径。
2. **降级天然成立**：没有框架，就没有"框架没加载导致页面空白"的问题。
3. **与设计约束一致**：视觉与交互由 token 与 CSS 承担，不需要组件库的主题系统。
4. **降低长期维护风险**：框架大版本升级会牵动全部组件；本项目需要"几年后仍能构建"。

## 影响

- 交互代码需要自己处理生命周期与幂等（例如视图过渡后的重复初始化），见 [前端架构 §3](../architecture/frontend-architecture.md)。
- 复杂表单（如评论）交给 Waline 客户端，不自建。
- 允许的例外：**构建期**集成（Markdown 插件、图片优化、语法高亮、搜索索引）不受此限——它们不增加客户端运行时。
- 判断标准：新增依赖若会被打进客户端 JS，默认拒绝；仅构建期使用的，走 [依赖策略](../engineering/dependency-policy.md) 评估即可。
