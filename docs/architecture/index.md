## 2. 一条硬边界

GitHub Pages **只提供静态文件**，不运行任何服务端逻辑。因此本项目把全部功能分为三类执行环境，任何新功能必须先归类再设计，归类失败说明方案不可行：

| 执行环境 | 能力 | 典型功能 |
| --- | --- | --- |
| 构建期（Node 进程，CI 中） | 读文件、校验、计算、生成静态文件 | 内容聚合、分类/标签索引、搜索索引、阅读时间、热力图、TOC 数据 |
| 浏览器（静态 JS） | DOM、滚动、存储、Fetch | 主题切换、搜索查询、灯箱、阅读进度、播放器、快捷键 |
| 外部服务（必须有独立后端） | 持久化与写入 | 评论（Waline）、可选的浏览量统计 |

判据：**需要写入并跨用户持久化的功能，永远不能放在前两类**。详见 [ADR-0007](../decisions/0007-static-dynamic-service-boundary.md)。

## 3. 与其他板块的关系

- 需求边界由 [需求清单](../product/requirements.md) 定义，本板块只回答"怎么实现"，不新增功能。
- 视觉与交互约束来自 [设计板块](../design/index.md)，架构不得绕过 token 与交互准则。
- 工程落地细节（构建、测试、依赖）在 [工程板块](../engineering/index.md)。
- 每个重大取舍都应在 [决策记录](../decisions/index.md) 留一条 ADR；只写在这里的决策等于没决定。
